# Review: upstream v1.0.2 to v1.6.0

Reviewed 2026-11-11 against `dree007/caddy-visualizer`. Target tag `v1.6.0` = `3352531cd1f397150c6c569497408b9185fdf599`.
`v1.0.2` = `57e5128` is an ancestor of it, so upstream did not rewrite history. No tag newer than 1.6.0 existed;
`upstream/main` had one later README-only commit (`07f2ece`), not included.

**Verdict: GO.** No critical or high findings. Two medium findings (new egress, an unguarded auth switch) are
handled by documentation and by this deployment's shape. Nothing in the kit needed a code change.

Release notes were treated as claims and checked against the code. Where a claim could be checked it held
(Next 16.4.2 and zod 4.6.7 in `package.json`, basic auth stored as a bcrypt hash and hidden in the preview,
`AUTH_DISABLED` refused with `ALLOW_INSECURE_LAN_HTTP`, header placeholders restricted to a fixed list).
Security-fix claims about Node and Next themselves were not verified, only the versions.

## Findings

### Critical, high

None.

### Medium

**M1. New outbound traffic from certificate checks.**
`src/modules/certificates/probe.ts` (DNS lookup at line 69 to 70, `tls.connect` at line 158 with
`rejectUnauthorized: false`) and `src/server/certificates/checks.ts` (interval and first-run delay at lines 30
and 31, started from `src/server/startup.ts`). The project requires that the only outbound traffic is the Caddy
admin socket. These checks add DNS queries and TLS handshakes to port 443, every 6 h, 60 s after start, and on
"Check now". There is no switch to turn them off.
Mitigations in the design: targets come only from Caddy's running config (`candidates.ts`); the host is resolved
once and the handshake goes to exactly the checked address; loopback, link-local, multicast and reserved ranges
are never contacted; private ranges only for names under `CERT_CHECK_PRIVATE_DOMAINS`; wildcard names are never
probed; at most 100 hosts, 6 s timeouts, no HTTP request.
Failure scenario for this deployment: someone adds an explicit site `www.example.org` to the Caddyfile. Every 6 h
CT109 resolves it and connects to its public address on 443 (a TLS handshake, certificate read, no payload).
Not a leak of data, but it is egress the project did not have.
Verified (smoke test 2, real Caddy 2.11.4): a wildcard-only Caddyfile gave `[certificates] checked 0 host names`
and no rows; two named sites resolving to `127.0.0.1` and `10.255.255.1` were blocked without a connection.
Decision: accept. The live Caddyfile is one wildcard site, so the feature is inert. Documented in
`deploy/ct109/README.md`. If egress must be blocked outright later, `IPAddressDeny=any` with
`IPAddressAllow=localhost` in the unit is the obvious lever (the probe would then report DNS failures). Untested:
it needs cgroup BPF support, which an unprivileged LXC may not have.

**M2. `AUTH_DISABLED` is only guarded when `BIND_ADDRESS` is passed in.**
`src/server/env.ts` lines 54 to 60 and 146 to 161; `docker-compose.yml` is the only place that sets
`BIND_ADDRESS`. In a native install the variable is absent, so the app starts with the login off and only logs a
warning (`src/server/startup.ts`). `src/proxy.ts` then skips every session check except the Origin check.
Failure scenario: someone adds `AUTH_DISABLED=true` to `/etc/caddy-visualizer/env`. Anyone who can reach the UI
host name can rewrite the Caddyfile through the app, with no login.
It is off by default and the value must be set explicitly. Mitigation: the env example now carries a "do not set"
note (this review's kit change).

### Low

**L1. `header_up` values are stored in plain text.** `src/modules/caddy/upstream-headers.ts` lines 47 to 91
(`isSensitiveHeader` only flags likely credentials). Values live in the `caddy_sites` row and in every revision
snapshot, and are visible in the UI. Scenario: an API key put into a header value is readable by anyone with
database or UI access and survives in revision history. README now says not to put secrets there.

**L2. Skipping upstream certificate verification is a per-site option.** `src/modules/caddy/generator.ts` lines
155 to 178. Operator-chosen, limited to `https://` upstreams (enforced in the schema and the generator).

**L3. A rollback must restore the database backup.** Migrations 0007, 0009 and 0011 rebuild `caddy_sites`
(copy, drop, rename). Verified: rows survive, integrity and foreign-key checks are clean, and no table has a
foreign key to `caddy_sites`. Verified: the 1.0.2 build starts and answers health on a migrated file. Not
verified: what it does with rows made by new features. `install-release.sh` restores the backup on a failed start.

**L4. Upstream ships no tests.** No test files in the `v1.6.0` tree and no `test` script. Assurance comes from
the type-checked production build plus the kit's smoke tests.

### Info

- Renderer safety for new Caddyfile output (`src/modules/caddy/caddyfile.ts`): every token is re-checked against
  a whitelist at render time; header text allows only fixed placeholders (`{host}`, `{remote_host}`,
  `{header.Name}` and similar) and no `{env.*}`, `{file.*}` or `{$VAR}`; redirects allow only `http(s)` URLs
  with fixed placeholders; backslash-before-quote cannot occur. No injection path found by reading.
- Auth: every exported server action calls `requireAccess()` (login, logout and the locale cookie excepted);
  `/api/health` is the only public route. `password.ts`, `sessions.ts`, `login-throttle`, `client-ip.ts`,
  `cookie.ts`, `ingest.ts`, `parser.ts`, `hostname.ts`, `site-inventory.ts`, `main-caddyfile.ts`,
  `managed-files.ts`, `admin-api.ts`, `upstream.ts` and `next.config.ts` are byte-identical to v1.0.2.
- Wildcard handling is unchanged: `hostnameCovered` / `manualConflict` in the apply engine still refuse
  UI-created sites for names a wildcard covers. The README wildcard section stands.
- The "add `import access_log`" feature (`caddyfile-sites.ts`) edits the main Caddyfile as text. Caddy checks
  the result before it is applied and it is recorded as a revision. Not exercised by the smoke tests.
- `npm audit --omit=dev`: 0 vulnerabilities. Lockfile: every `resolved` URL is the npm registry, no install
  scripts added; `allowScripts` still denies esbuild, better-sqlite3 and unrs-resolver.
- Dockerfile: only the distroless runtime digest changed; the kit uses the `build` stage (`node:24-bookworm-slim`),
  so the bundled Node is whatever that tag resolves to at build time (v24.22.3 on 2026-11-11).
- Memory: peak 229 to 230 MB RSS over two runs (1.0.2 build: 219 to 239 MB, so no measurable change) with
  every page rendered three times under the unit's 192 MB heap cap. No new caches or workers beyond the
  6-hourly certificate run.
